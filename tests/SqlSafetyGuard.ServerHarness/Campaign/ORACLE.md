# Campaign oracle and limits

The campaign extends **CoverageDatabase.Capture**, the existing strict coverage exact-row/catalog fingerprint. It does not replace it with a checksum-only implementation. Strict coverage keeps its existing entry points. Campaign data is trusted executable test code, not hostile SQL isolation.

## Recorded evidence

* Exact sorted typed row representations (including nulls, binary values, and duplicate multiplicity), plus the existing 60+ catalog queries: definitions, columns, indexes, constraints, schemas, users, role membership, permissions, database options, temporal table metadata, partitions, cryptographic catalogs and Broker metadata. Sequence current_value **and last_used_value** catch first use; identity last_value catches burned identities even when rows roll back.
* Database-qualified object definitions and sequence state are keyed individually. Table row changes name their actual base table, including audit/temporal side effects. Metadata catalogs without a safely attributable object are explicitly named as catalog changes, not guessed table names.
* Per-base-table leaf insert/update/delete counter deltas from sys.dm_db_index_operational_stats (heap or clustered index only) detect physical DML work even after rollback or same-value UPDATE. These are reported separately from logical persisted changes. A positive delta means observed physical work, not proof of a net committed change. Changed=yes is deliberately conservative: logical change OR physical write evidence.
* Queue contents (conversation handles, sequence numbers, message types and binary bodies), queue/service definitions and conversation endpoints.
* Server principals, permissions/roles, configuration configured/in-use values, linked servers, non-run database states, endpoints and XE session names. Run-owned temporary databases/logins are excluded to allow independent worker provisioning. No server state is reset on the shared instance.
* Permanent (non-#) tempdb object metadata and exact typed table rows. Changes are currently attributed to tempdb.<permanent-objects>, not individual tempdb objects. Local/global # objects are intentionally excluded from permanent-write detection.
* In verified Docker mode, SHA-256/path inventories of non-data/log files directly under /var/opt/mssql/data and /var/opt/mssql/backup. BACKUP/export effects there survive unchanged database fingerprints. Never inspect arbitrary host paths.
* Session evidence is read **before any observer resets SET options**, and before connection disposal: @@TRANCOUNT, @@OPTIONS (including IMPLICIT_TRANSACTIONS), ORIGINAL_LOGIN, SUSER_SNAME, USER_NAME and current database. Differences are compared with the requested context, so the harness's intentional impersonation is not a leftover. Closing the nonpooled connection rolls back open transactions, releases locks and discards the execution context. Persisted snapshots then use fresh independent admin connections.
* Every case records execution/observation/cleanup errors, stage, elapsed SQL/total/analyzer milliseconds, classification and finding targets, before/after database hashes, logical objects, physical-write objects and session leftovers. SQL errors never earn PASS. A false green observed before a SQL error remains FALSE GREEN, with the error retained.

## Target contract

WRONG TARGET means at least one concrete modified object is neither named by a red finding nor reachable through the pre-execution effect graph. AnalyzerHost preserves the analyzer's ResolvedTarget (not just its alias token). Synonyms, single-base views, enabled trigger named INSERT/UPDATE/DELETE/MERGE targets, cascading foreign keys and temporal-history edges explain INDIRECT EFFECT. Every changed concrete object must be reachable. Opaque Broker variables/no targets yield UNRESOLVED TARGET. Catalog-only changes remain scope evidence. Graph edges are operation-nonspecific and limited to the simple world identifiers; alias/dynamic trigger targets and arbitrary remote metadata remain limitations.

Wave 3 also retains schema-transfer pre/post-name edges and validates owned SgLoop four-part targets before adding remote attribution edges. OPENQUERY/OPENROWSET expressions with unmatched changed objects are opaque UNRESOLVED TARGET, not fabricated concrete WRONG TARGET evidence. The provider's arbitrary SQL is not assumed to identify a statically resolved base object.

Parallel SgExt_* objects and foreign database availability-state drift are excluded only from the unrelated-server observation query. Raw external observation remains in the receipt; owned/system/tempdb/file observations are never discarded by that filter. This permits coexistence with the separately owned extension lane without hiding campaign mutations.

EXTERNAL CHANGE requires error-free execution and exact equality of all owned rows/catalogs/object definitions/operation counters/tempdb/files and every server query except the unrelated-database metadata query. That external evidence remains Changed=true and is not reused after a before/after external difference. The host's unrelated AdventureWorks2012 was observed changing ONLINE/RECOVERING; it was never modified by this work. Any simultaneous owned write or other server-state change fails this exclusion.

## Worker reuse and isolation

A worker retains a four-database set only after successful execution with exact before/after equality, no logical/physical write, no SQL/observer errors, no session leftovers and no setup SQL. The next case takes a full snapshot and compares against the saved pristine state **before executing case SQL**; an owned mismatch aborts, never runs against dirty state. Only unrelated database metadata drift is ignored for that pristine check. Every changed/error/setup/shrink case discards the set and restores all four databases. Case connections remain nonpooled; only admin master/results connections are pooled. This is conditional reuse, not snapshot/page-level rollback. Asynchronous/unobserved effects remain oracle limitations.

Catalog queries retain exact typed/ordered content and labels but share a command with NextResult; missing result sets fail capture. Observer read deadlocks alone are retried twice; executed case SQL is never retried. SQL results are saved every case; JSONL/report flush every 100 completions and at clean termination. SQL is authoritative after abrupt termination.
NOISE means a non-green classification with no observed write; no-op/unreachable/rolled-back cases can warrant caution. Session leftovers are orthogonal, not permanent database writes. Expected-classification mismatches are a separate report flag and fail the exit gate. A green SELECT may legitimately leave IMPLICIT_TRANSACTIONS open; this is reported, not silently promoted to a permanent write.

## Blind spots / not a completeness certificate

* Operational counters are volatile and can reset on eviction/rebuild/restart; SQL Server exposes aggregate counters, not a durable per-session audit trail. They can miss deleted objects or short-lived rolled-back DDL. Counter loss is not proof of no physical write. Same-value UPDATE is conservative physical-write evidence, not a false-green proof of persistent data corruption.
* No fn_dblog parsing, durable Extended Events DML audit, or transaction-log completeness claim. A transaction that writes then erases the logical effect may escape if DMV evidence disappears. An unavailable observer is an error, never no-change evidence.
* Persistent snapshots observe after session closure, not dirty in-session versions. Open-transaction writes rely on DMV evidence (and identity/sequence effects); session transaction count is retained. Restoration creates fresh files/object state for each shrink trial.
* Not every catalog is observed. Server XE **names**, not full definitions, are currently compared; credentials/secrets, key material, buffer/cache changes, login audit events, SQL Agent job state and arbitrary external services are not exhaustively fingerprinted. Unsupported features must have explicit feature-specific assertions in a separate isolated corpus.
* File inventory does not recursively scan the container or see external mounts/network destinations. mdf/ndf/ldf physical rewrites are excluded. Files made and removed within one case can escape. No host BACKUP permission is granted.
* Async Broker delivery/activation may continue after capture. No queue-drain/stability proof is made. Queue inspection can time out on locks; that fails observation. Concurrent unrelated host activity may create server/tempdb noise; privileged campaigns are serial and disposable, and shared-instance cases are restricted to their own database sets.
* Catalog creation/deletion transiently undone within the same case and settings outside @@OPTIONS (ROWCOUNT, TEXTSIZE, LANGUAGE, DATEFORMAT, CONTEXT_INFO, SESSION_CONTEXT, isolation level) require dedicated assertions. The current generic session oracle does not claim those are covered.
* Linked-server effects outside the owned container are prohibited. The Docker loopback probe targets only run-owned databases. Normal SQL functions may write table variables; SQL Server does not allow ordinary T-SQL UDFs to perform persistent table writes. CLR/external side effects are not represented by the seeded functions.
* The Local-session mutex prevents concurrent harness invocations in this Windows session. Campaigns also hold an exclusive SQL application lock in master across Windows sessions; other harness modes and remote tooling do not participate. Workers within one campaign are intentionally concurrent but own distinct database sets. Do not run another SQL harness from another login/session against this instance.

Negative controls have controlVerdict=ReadOnly, retain the actual analyzer verdict, and are counted separately in every outcome table. Their expected failure exercises detection/shrinking, and must never be reported as an actual analyzer false green.

## Confirmation replay (single worker)

Every result a parallel worker could have disturbed was replayed with `--workers 1`: all green-verdict EXTERNAL CHANGE results (all of
them were `<server-state>` only), every FALSE GREEN and every CRASH.

So the 1,081 green "external" server-state changes, the 8 server-state false greens and the 20 crashes were all caused by
concurrency in the harness, not by the analyzed scripts.

## Crashes

- 16 generated + 3 full-access: `Cannot continue the execution because the session is in the kill state` while cloning a database
  set (before the case ran); 1 generated: the reuse isolation control refused a set that differed from its pristine snapshot. All
  passed on single-worker replay.
- 1 isolated: `DBCC DEBUGBREAK` stops the container's SQL Server by design; the launcher resumed in a fresh container.

## Harness follow-ups

1. Server-permission snapshot: join `sys.server_permissions` to `sys.server_principals` and exclude both clone logins and grants whose
   grantee no longer/not yet exists, so concurrent clone setup cannot appear as a server-state change.
2. Classify server-state changes coinciding with another worker's clone lifecycle as EXTERNAL CHANGE consistently (today it depends
   on whether a database was also created/dropped at the same moment), or serialize clone login creation with case execution.
3. Retry a clone once on `session is in the kill state` instead of recording CRASH.

## Policy short list for the company

These are behaviours the run observed or confirmed. None is a bug against the current design; each needs a decision. Typed
confirmation stays disabled either way.

1. **Allow-listed objects with side effects.** Allow-listing `sales.Orders`, a view or a synonym also authorizes its trigger writes
   (`audit.Changes`), cross-database writes (`Archive.dbo.Counter`), temporal history and sequence advances. Does authorizing the entry
   point authorize everything it reaches?
2. **Trusted procedures.** A trusted procedure is shown green even when it writes. Should trust mean "authorized", a different label,
   or a claim that it has no effects?
3. **`tempdb` opt-in (`TempdbIsTemp`).** With the setting on, permanent shared `tempdb.dbo.*` objects are green. Keep the opt-in,
   restrict it to session-local objects, or remove it?
4. **`RAISERROR … WITH LOG`.** Writes the server error log but is green. Treat log writes as writes?
5. **Session-state changes that outlive the script** — `EXECUTE AS`/`SETUSER`, `SET IDENTITY_INSERT`, `SET IMPLICIT_TRANSACTIONS`/
   `ANSI_DEFAULTS`, `sp_set_session_context`, session-owned `sp_getapplock`, global `##temp` tables. All green today.
6. **`ROLLBACK` of a caller's transaction.** Green today, but it can discard work the script did not start.
7. **Metadata maintenance** — `UPDATE STATISTICS` (yellow) and `DBCC CHECKDB` (green): warn or not?
8. **Service Broker `SEND`.** Which object should the red finding name: the dialog, service, queue, or all of them?
9. **Red-only mode.** Unknown procedures produce no prompt in Red mode by design. Acceptable trade-off?

The first IAP process started at **08:14:31.5863901 UTC** and exited after its backend connection check failed. After

cleanup at **08:16:08.7096249 UTC**. It did not restart a VM/controller, overlap jobs or extend the deadline.

The helper incorrectly treated the second early backend-readiness failure as terminal rather than allowing the configured
fifteen-minute Windows/SSH startup window to elapse. Port unreachability does not establish whether Windows OpenSSH was
missing, still initializing or failing; no authenticated guest session or serial diagnosis was retained. No missing IAM
permission was demonstrated. The repeated startup blocker triggered the bounded stop rule, with no further VM attempt.

The smallest useful correction before another attempt is to preserve the absolute deadline while allowing Windows/SSH
readiness to finish within the existing bounded window, using guest startup/serial observations to distinguish expected
initialization from an actual service/network failure. A readiness probe should not consume the sole recovery attempt
immediately after VM creation. No such correction was run against another VM in this attempt. The previous 22.5 VSIX
installer hang therefore remains unresolved; the planned fresh-install/restart comparison never reached SSMS setup.
